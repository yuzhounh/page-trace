## 当前任务：首屏包含油猴刚保存的笔记

目标：同一浏览器配置内，通过油猴成功保存笔记后，打开管理页的首屏就包含这些新笔记；云端确认内容一致时，列表不重复重画。

### 修改前原因（历史源码行号）

- `pagetrace.user.js:165-261` 的 `saveToFirestore()` 直接写入 Firestore，成功后清理待提交记录并返回，没有更新管理页缓存。
- `index.html:3546-3567` 使用当前站点的 `localStorage` 存完整笔记列表；`3593-3628` 在登录恢复前直接显示这份缓存。
- 登录恢复后，`index.html:3826-3863` 建立云端监听。每次快照都覆盖 `notesData`、保存缓存并调用 `renderList()`；`4477` 使用 `innerHTML` 重建列表。
- 油猴当前为 `@run-at document-idle`。仅增加一个晚到的缓存消息仍可能造成旧列表先显示、新列表再显示。
- 油猴在各网页运行，但当前没有持续监听全部云端笔记；保存确认与网页管理页的全量缓存是两个独立流程。

`localStorage` 按来源隔离，普通网页里的脚本不能直接写入 PageTrace 站点的同名缓存。推荐使用同一油猴脚本的 GM 存储传递新增记录，再由可信管理页桥接读取。[MDN localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)、[Tampermonkey GM 存储](https://www.tampermonkey.net/documentation.php?locale=en&q=GM_values)。

### 步骤 1：成功保存时记录共享新增笔记

- 在 `saveToFirestore()` 已获云端成功响应，或 409 后确认已有文档内容一致之后，写入 GM 存储；两种保存入口都经过此函数。
- 按 `projectId + uid + documentId` 保存独立记录，包含原文、标题、URL、创建时间、状态、来源和本地确认信息。使用现有稳定文档 ID 去重，不能按 URL 去重，因为同一网页可以保存多条笔记。
- 独立记录避免多个网页同时读写整份数组时互相覆盖。已有待提交记录继续与成功缓存分开；超时或失败的保存不标成成功笔记。
- 缓存写入异常不能把已成功的云端保存报告成上传失败；保留云端结果，并允许管理页随后从云端补齐。

验收：管理页关闭时在两个网页成功保存不同笔记，两条共享记录都保留；重试不重复，失败不冒充成功。

### 步骤 2：合并完成后再显示首屏

- 首屏数据为“上次完整云端快照 + 同账号油猴成功新增记录”，按文档 ID 合并和排序，一次显示。
- 将轻量缓存桥接提前到 `document-start`，浮窗仍在 DOM 可用后挂载。提前注入只提高取得缓存的机会，页面仍须处理脚本晚到和未安装的情况。[Tampermonkey 注入时机](https://www.tampermonkey.net/documentation.php?locale=en&q=run_at)。
- 调整 `initFromCache()`：先取得本地桥接结果再渲染；请求须有界，若桥接未就绪则显示加载占位并继续读取云端，避免立即展示已知可能缺少新增笔记的旧列表。离线时可明确显示缓存副本。
- 复用可信域名、准确路径、同窗口、会话 nonce 和账号检查；笔记缓存仅交给可信管理页。账号不一致时不能合并，也不能用缓存账号代替已恢复的真实登录状态。
- 首次使用、清空缓存或换管理页域名时，没有完整历史快照就需要从云端建立基线；脚本的新增记录不能当作所有历史笔记。
- 页面已打开时，可用 `GM_addValueChangeListener` 通知有新保存记录，然后按 ID 合并，保持滚动、筛选和展开状态；通知后读取记录，不能把单个通知值当作唯一笔记来源。

验收：先有历史快照，再关闭管理页并通过脚本新增笔记；重新打开时首次笔记渲染包含新旧笔记。覆盖脚本早到、晚到、未安装和账号切换。

### 步骤 3：云端同步只更新实际差异

- 保留实时同步用于其他设备的新增、修改、删除以及本地记录的最终核对。
- 使用 `includeMetadataChanges` 和 `snapshot.metadata.fromCache` 区分 SDK 本地快照与服务器确认；SDK 的空或旧快照不能抹掉已有完整快照和刚确认成功的新增记录。[Firebase 实时监听](https://firebase.google.com/docs/firestore/query-data/listen)、[Firebase 快照来源](https://firebase.google.com/docs/firestore/manage-data/enable-offline)。
- 内容统一时间格式后比较，覆盖 ID、正文、标题、URL、状态、创建/更新时间、删除字段和来源。内容一致只更新同步状态及缓存确认信息，跳过列表重画；有差异时更新相关显示，保留当前阅读状态。
- 服务器确认后更新完整快照，并对已核对的新增记录做结算。管理页编辑、软删除、恢复和永久删除也须更新缓存状态；旧新增记录不能在下一次打开时恢复已删除的笔记。
- 结算只处理本次云端结果已覆盖的记录，不能清除同步期间刚发生的新保存。多标签页和不同管理页来源的快照、确认及清理必须保持一致，避免旧快照覆盖新结果。
- Token 刷新时若账号和监听未变，不重复解绑并重建笔记监听；账号切换时旧回调不能更新新账号列表。

验收：首屏与服务器数据相同不重画列表；新增、修改、删除正确更新；同步期间的新保存不丢失；原有保存重试及认证测试仍通过。

### 补充决策：版本核对与减少正文传输

用户问题：后台核对是否重新上传本地笔记或下载完整正文，能否只比较 ID、创建时间和修改时间，以及这样做对项目是否有价值。

当前后台读取不会上传整份本地缓存。页面的监听查询覆盖当前账号整个 `notes` 集合；初次建立监听会获取匹配的文档数据，之后持续监听主要接收变更。`snapshot.docs` 是 SDK 在本地维护的完整结果，不能据此认定每次回调都从网络重下载全部笔记。相同内容不重画是显示优化，本身不减少已发起请求的正文传输。[Firebase 实时查询机制](https://firebase.google.com/docs/firestore/real-time_queries_at_scale)。

现有字段已包括文档 ID 和 `createdAt`，网页编辑时写入服务端 `updatedAt`；但软删除和恢复没有更新 `updatedAt`，油猴创建时间来自客户端。现有业务时间字段不能直接作为完整版本协议。创建时间相同仅确认创建信息相同；判断未改动还要求一个覆盖全部变更的可靠版本。

Firestore REST 文档自带系统 `createTime` 和 `updateTime`，新文档的 `updateTime` 等于 `createTime`，每次文档变化自动更新。建议以“同账号 + 同文档 ID + 相同服务端 updateTime + 已缓存该版本完整正文”判断缓存有效，不需要逐字比较正文。保留系统版本的完整精度，不转换成毫秒后再比较。版本缺失的旧缓存需要补齐一次；409 保存重试的内容验证仍保留，它承担的是确认待提交内容而非日常缓存核对。[Firestore Document](https://firebase.google.com/docs/firestore/reference/rest/v1/projects.databases.documents)。

进一步减少正文传输的可行方式：先通过 REST 的字段掩码读取完整文档目录，只返回 ID 对应路径、系统创建/更新时间及需要的少量状态字段；版本相同沿用本地正文，只下载缺失或版本变化的文档。这个过程仍读取全部目录信息，但不传输未变化的正文，也不上传缓存正文作核对。[Firestore documents.list](https://firebase.google.com/docs/firestore/reference/rest/v1/projects.databases.documents/list)。

必要条件：

- 必须以完整成功读取的目录核对永久删除；分页未结束、请求失败或同步期间的新保存不能被误判为删除。
- 缓存正文必须与保存的服务端版本对应；较旧的异步响应不能覆盖已经确认的较新版本。
- “较新覆盖较旧”适用于已由服务器确认的版本。未上传草稿仍是独立待提交状态，不能凭电脑时间较新自动覆盖云端或重新上传缓存。
- 当前 Web SDK 的快照接口不公开系统 `updateTime`，现有集合监听也不支持仅返回选定字段。要实际减少正文下载，须调整读取路径；先读目录随后照常启动整个 `notes` 集合监听，会再次引入全量初始正文读取。[Web DocumentSnapshot](https://firebase.google.com/docs/reference/js/v8/firebase.firestore.DocumentSnapshot)、[Web Query](https://firebase.google.com/docs/reference/js/v8/firebase.firestore.Query)。
- REST 目录核对可以在打开、回到前台或手动刷新时执行，但它本身不提供持续实时推送。若仍要维持现有跨设备实时更新体验，需要设计轻量变更通知或兼容的增量监听，覆盖全部写入和删除入口；这属于下一阶段的同步改造。

价值与本轮建议：优先完成步骤 1–3，它们直接解决本机油猴保存后首屏缺少新笔记、重复重画和阅读位置被打断的问题。服务端版本可随保存响应一并保留，成本较小；独立改造为目录先行、正文按需下载，主要收益是正文较长、笔记较多时的后台传输与解析节省，对其他设备恢复缓存也有帮助。它不能省掉鉴权和网络往返，也不会自动减少查询的文档数量。当前未测量真实笔记数量、正文总量或延迟分解，不能声称两三秒主要由正文下载造成。

本轮不把完整版本同步协议设为首屏修复的前提。缓存衔接已经实施并通过上述测试；若随后确认重复正文传输有明显成本，再独立实施目录先行同步，避免同时引入第二套不一致的实时更新流程。该段为下一阶段方案评估，正文按需下载尚未实施。

### 正文按需下载：增量价值评估（2026-10-14）

用户补充：目前少于 500 条笔记，主要是短速记。结论：按需下载存在后台传输收益，但目前不足以优先改造同步协议。保留已完成的首屏合并优化，先验证实际打开体验。

测试方式：运行 [离线评估脚本](../tmp/body-sync-benchmark.cjs)，输出 [结果 JSON](../tmp/body-sync-benchmark.json)。构造 9 个模拟场景，正文为 256B、1KiB、2KiB、16KiB，分别覆盖无变化、1% 变化及服务端版本缺失。执行现有 `serializeNoteForCache`、`noteContentSignature` 和 `applyNotesData` 生产函数，与“版本目录 + 变化正文”原型比较。每项预热 3 次、计时 9 次，报告中位数；所有场景的合并正文与模拟云端结果一致。脚本未访问真实笔记或网络。

下表均为模拟数据。JSON/GZIP 体积用于比较传输量级，并非实测 Firestore 协议流量；CPU 包括 JSON 解析、现有数据应用与缓存 JSON 序列化，不包括鉴权、网络、数据库、浏览器存储 I/O 和 DOM 渲染。版本齐全的场景假设目录一包返回、变化正文一次批量获取，实际分页或逐条请求会增加成本。

| 模拟场景 | 全量/按需 JSON | 全量/按需 GZIP | 全量/按需本地处理 |
|---|---|---|---|
| 500 条 × 256B，无变化，版本齐全 | 361.3 / 99.6 KiB | 36.4 / 4.3 KiB | 6.27 / 0.20 ms |
| 500 条 × 1KiB，无变化，版本齐全 | 747.0 / 99.6 KiB | 106.6 / 4.3 KiB | 7.91 / 0.19 ms |
| 500 条 × 256B，5 条变化，版本齐全 | 361.5 / 103.5 KiB | 36.4 / 5.2 KiB | 6.08 / 5.42 ms |
| 500 条 × 256B，原缓存没有服务端版本 | 361.3 / 460.9 KiB | 36.4 / 40.7 KiB | 5.74 / 6.89 ms |
| 1,000 条 × 16KiB，10 条变化，版本齐全 | 16,924.0 / 369.0 KiB | 2,969.5 / 38.7 KiB | 94.46 / 80.02 ms |

决策依据：

- 首屏使用本地缓存与共享新增记录，已经不必等待正文同步；正文按需下载不会消除当前首屏路径中的新一轮等待，主要影响后台核对。
- 少于 500 条短速记时，模拟全量本地处理约 4–8ms。压缩响应可节省约 20–102KiB，比例很高但绝对体积有限。发生变化时须先获取目录、再请求正文，额外网络往返可能超过节省的传输时间；不能据此承诺真实页面提速。
- 缓存版本缺失时仍须补齐正文，首轮可能多传一份目录；当前历史笔记及网页 SDK 编辑后的缓存没有保证都带系统版本，不应仅按理想的 100% 版本覆盖估计收益。
- 现有持续监听主要传输变化文档。目录请求自身不提供实时通知，直接用轮询替代会改变跨设备更新体验；若保留原有全量初始监听，新增目录请求不会避免其正文下载。[Firebase 实时查询机制](https://firebase.google.com/docs/firestore/real-time_queries_at_scale)。
- 只选择元信息不会自动减少文档读取数量。此方案的简单目录读取仍访问全部笔记，之后获取变化正文会增加读取；例如模拟 500 条、5 条变化时是约 500 + 5 次文档读取。这里未计索引、规则和最小计费，不能将流量下降当作数据库读取费用下降。[Firebase 计费说明](https://firebase.google.com/docs/firestore/pricing)。
- 上千条长摘录时，模拟压缩响应可从约 2.90MiB 降到 0.038MiB，才出现明显的后台传输收益。以后若真实同步数据达到数 MiB、后台核对明显拖慢，或用户用途转为大量长文剪藏，再重新评估。

本次仅新增临时评估脚本与结果，并更新本计划；业务源码、油猴版本和现有 52 项测试对应实现均未变动。未访问真实云端或浏览器缓存，未推送、部署，也未把模拟网络体积/CPU 耗时当作真实加载耗时。

### 按月云端加载与全局搜索：原方案与实施边界（2026-10-14）

用户目标：默认只加载当月正文，切换月份再加载相应月份，保留全局搜索。下述原方案已按授权实施，当前验证结论见本文件顶部 1.13.0 记录；全文索引与精确全历史实时统计仍未纳入本轮。

结论：该方案比逐条正文版本核对更直接地改善长期日常浏览。推荐第一版做“按月浏览 + 首次使用全局搜索时按需加载历史全文”，属于中等改动。它减少日常启动和切月的读取范围；首次全局搜索仍承担历史正文读取，不能同时承诺搜索也不下载全部历史。

#### 1. 云端查询与显示范围

- 默认查询现有 `users/{uid}/notes` 集合中 `createdAt >= 月初` 且 `createdAt < 下月月初` 的文档，按 `createdAt` 倒序监听。月份按创建时间划分，编辑时间不改变所属月份；不需要给每条云端笔记新增月份字段或迁移数据库。[Firestore 排序与范围查询](https://firebase.google.com/docs/firestore/query-data/order-limit-data)。
- 月初边界与页面现有日期分组使用相同时区，避免北京时间月初附近的笔记落入错误月份；缓存分区也必须使用相同口径。不能直接用 UTC 月初替代本地月初。
- 第一版每个选中月加载该月全部正文，继续沿用已有的 50 条显示批次。月内云端分页先不加入，因为每月通常只有数百条，整月加载能简化实时同步、月计数和“复制当前筛选全部笔记”。未来遇到单月数千条时再用文档游标分页。[Firestore 查询游标](https://firebase.google.com/docs/firestore/query-data/query-cursors)。
- 当前多数新建记录没有 `isDeleted` 字段，不能直接增加 `isDeleted == false` 查询，否则会漏掉这些正常笔记。月查询包含该月软删除文档，继续在界面过滤；回收站使用独立查询。
- “某年全部月份”用该年的日期范围；“全部年份/全部月份”、跨年指定月份等全历史视图由用户显式选择时再加载全量，保留原筛选含义。
- 当前月没有笔记时仍保留月份选择器并显示空月，不能依据未加载的其他月份自动跳转或隐藏导航。

#### 2. 按月缓存与实时同步

- 将当前账号单份全量缓存改成账号、时区口径、查询范围对应的分区缓存。当前月份、年份范围、全历史搜索、回收站分别记录加载完成状态，不能让“当月已加载完”冒充“全部历史已加载完”。
- 切月先显示该月缓存与同范围油猴成功保存的记录，再建立该月监听；关闭上一个月监听，只保留当前浏览范围的订阅。快速连续切月时，用请求代数丢弃晚到的旧月份回调。
- 历史月份缓存设总容量/最近使用上限，避免随使用年限持续增长；旧缓存再次访问时重新同步。首次兼容现有全量缓存，可在本地按月拆分，无需读取或改写云端数据。
- 油猴当前 `sendSharedCache()` 会读取、发送全部成功保存记录。必须一并增加请求范围过滤，并将共享记录按月份索引或分区，避免云端已按月加载、首屏桥接仍读取全部历史正文。保留独立文档 ID、并发保存和现有重试行为；旧缓存格式一次性兼容。
- 成功记录的核对与删除判断也限定当前查询范围。服务器月快照中不存在某个其他月份的 ID，不能据此认定该历史笔记被删除。
- 保存响应自带的服务端版本继续保留；本方案不要求再增加逐条版本目录请求。

#### 3. 保留现有全局搜索

- 当前 `getSearchFilteredNotes()` 对标题、网址和正文执行忽略大小写的包含匹配。这不是现有 `Query.where()` 可以直接表达的字符串子串查询；当前 Web SDK 查询运算符没有相应操作。[Web SDK 查询运算符](https://firebase.google.com/docs/reference/js/v8/firebase.firestore)。
- 仅打开空搜索栏不下载历史；首次输入非空关键词时启动一次全历史加载，先搜索已有缓存，逐步补齐历史。明确显示仍在检索的状态，全部加载完成后才把数量或“没有结果”作为完整全局结论。
- 输入后续关键词复用已取得的搜索数据，不每敲一个字重新下载。查询切换只更新当前关键词，旧关键词的异步结果不能覆盖新关键词。
- 搜索完成后保留原有月份筛选及全局搜索语义；退出搜索恢复进入前的月份与其监听。全量搜索缓存与默认月缓存分开，不在下一次普通启动时解析或显示全部历史。
- 一万条文本的全局匹配可分批或移至后台处理，避免输入被长任务阻塞。首次全局搜索的云端读取仍与总笔记数相关，属于该简版的明确成本。
- 如果今后要求“全局搜索也快速，并且只返回命中笔记”，需要另建全文索引或更换查询能力。官方当前原生文本搜索要求 Firestore Enterprise 数据库、文本索引及 Pipeline API；不能作为现有 10.12.0 compat 客户端的简单查询过滤追加。[Firestore 文本搜索要求](https://firebase.google.com/docs/firestore/enterprise/text-search)。第一版不引入这项改造。

#### 4. 月份统计、导航及其他功能

- 当前 `getYearAndMonthStats()`、`getAllAvailableMonthPairs()`、年份/月数量、跳过空月的箭头，都从全量 `notesData` 推导。仅替换监听会丢失历史月份选项、错误计数或使旧月份无法选择。
- 推荐简版保持现有导航外观，改为按日历选择年月；准确展示已经完整加载月份的数量，未加载月份不伪装成 0 条。历史年份范围可通过最早/最新创建记录的小查询取得；箭头按相邻日历月切换，允许空月。
- 若必须完全保留“只列有笔记的月份、准确显示所有历史月份数量、箭头跳过空月”，需额外的轻量月份目录/统计。一次获取全部文档元信息仍会读取全体文档，不能把它计为启动读取次数下降；逐月聚合也增加请求且不能实时监听。更完整的月份统计需要维护汇总记录，并在所有保存、删除、恢复入口保持原子和幂等。[Firestore 聚合限制](https://firebase.google.com/docs/firestore/query-data/aggregation-queries)。这是比简版更大的可选范围，不应默默取消现有计数，也不应为统计在后台偷偷加载全部正文。
- 回收站打开时单独查询 `isDeleted == true` 的全历史回收站记录。恢复旧月份笔记要更新其月份缓存，清空回收站必须基于完整回收站查询，不能只清空当前月的删除记录。
- “复制当前筛选全部笔记”继续复制完整选中月/年或搜索范围，不能误改为仅复制已显示的 50 条；尚未完成的全局加载不能报告已复制全部结果。

#### 5. 收益与改动量

数量示例采用用户长期笔记规模作类比，不代表 PageTrace 已有相同数据：假设总量 11,897 条、选中月份有 300 个文档，不额外读取全历史目录，日常启动需读取的笔记文档从 11,897 降到约 300，约减少 97.5%。如果一次浏览三个各 300 条的月份，合计约 900 条，仍约减少 92.4%。数据体积还取决于各月正文长度；这些比例不是实测打开速度或精确账单。

日常浏览的云端读取、正文传输、反复解析/排序/比较和持久化缓存负担不再随全部历史同步增长。收益在总笔记达到上万条时明显，即使是纯文本也有效。首次全局搜索仍需加载全历史；若每次打开都立即进行全局搜索，累计读取收益会缩小。

简版主要涉及两个业务文件 `index.html` 与 `pagetrace.user.js`，另有相关测试及说明文档。修改约分为查询范围/缓存、导航统计、全局搜索、回收站与批量操作四块，不需要重写 Markdown 渲染、CSS 或 Android 原生登录。范围查询通常依赖自动单字段索引，实施时仍须验证现有项目索引配置。[Firestore 索引](https://firebase.google.com/docs/firestore/query-data/indexing)。若将修改后的网页交付 Android，需要重新打包内置资源；本轮不构建 APK。

推荐按可独立检查的步骤实施：先完成范围查询与分区缓存，再接入导航、全局搜索和回收站，最后回归验证。重点验证月初边界、快速切月、旧缓存兼容、并发保存、跨月编辑/删除/恢复、搜索历史命中、加载未完成提示及完整范围复制。只加两条日期过滤属于小改；完成这些依赖才是可用的中等改动。精确历史统计与快速云端全文搜索属于更大范围，第一版不建议一起加入。

该段保留方案决策与依赖说明；当前业务实现与自动测试已完成，具体证据见顶部 1.13.0 记录。Firestore 配置、真实云端数据、远端发布和 Android APK 均未变动。

### 适用范围与实施边界

该方案能让同一浏览器配置、同一油猴安装中成功保存的新笔记进入首屏。另一设备、另一浏览器或 Android 应用的变更仍需联网获取；油猴运行在普通网页时不会自动知道这些变更。首次建立基线和缺少脚本时也不能保证无网络等待。

## 后续建议：按优先级独立实施

### 1. 先调整触屏阅读与编辑字号

- 页面基础字号建议 14px；普通正文与剪藏正文统一为 15px，行高 1.6。
- 笔记标题建议 16px，保持中等加粗；新建/编辑输入框统一为 16px。
- 日期、字数、辅助说明保持 12–13px，避免所有文字都同样醒目。
- 在共享触屏层使用明确的字号变量，并处理手机媒体查询与 Android 的覆盖关系。当前大量规则使用固定 px，仅修改根字号不会统一放大。
- 验证不同笔记类型、Markdown、编辑窗口及窄屏换行。这个步骤只调整阅读层级，不修改笔记数据。

### 2. 再协调导航与卡片留白

- 日期导航文字建议从 12px 调到 14px，按钮目标高度 40–44px。
- 顶部品牌建议 17–18px，顶栏约 48–56px；图标按职责保留 20–22px。
- 笔记卡片上下留白建议 14–16px、左右留白约 16px，不机械地把全部间距乘以固定倍率。
- 工具栏允许在最窄屏幕按功能分组换行，避免通过缩小文字或点击区域勉强维持一行。
- 长按菜单继续保持 280px 与 56px 操作行，不随主界面变大再次拉宽。

### 3. 检查 Android 系统字体适配并发布

- 布局适配完成后，再评估将固定 `setTextZoom(100)` 改为跟随系统字体倍率；需同时验证默认字体和较大字体、横屏与键盘弹出状态。
- 先以默认系统设置确定基线，再判断是否需要提供字号选项。第一轮无需新增整体缩放设置。
- 不建议使用全局 CSS zoom、transform scale、改变 initial-scale，或直接将 WebView 字体一律放到 110%：它们会连带改变菜单、弹窗、工具栏布局或字体与控件间的比例。
- 后续发布 Android 版本需要重新打包，因为 Gradle 会将网页/CSS 复制进 APK；网页发布不会自动更新已安装 APK 的内置页面。
